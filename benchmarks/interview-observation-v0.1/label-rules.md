# observation 标签口径（v2，2026-11-12 修订）

> **v2 变更（外部评审后）**：把 `inconclusive` 的适用范围收窄为「**评测上下文本身不可用**」，
> 不再用它表达"回答太弱/太短/绕开问题"。那类属于 `needs_probe`。
> 变更原因：v1 会让"回答不好"和"问题不可评价"混成一个标签，导致 gold 摇摆（OBS-006 / ABS-004/005/006 都卡在这条边界上）。

## 0. 三个标签的唯一正式定义

```text
supported_in_this_answer
  当前回答本身提供了足够证据，满足被评价的参考要点。
  它不认证用户的总体能力，也不认证个人经历的真伪。

needs_probe
  问题与参考是可以评价的，但当前回答错误、不完整、自相矛盾、答非所问或以其他方式不足。
  应当继续追问/补充证据。

inconclusive
  因为评测上下文本身不足或含混，无法做出可靠判断：
  缺参考（has_reference=false）、缺前置上下文、问题本身无法成立。
```

判定时**先看上下文是否可用**：上下文不可用 → `inconclusive`；上下文可用 → 再看回答 → `supported` 或 `needs_probe`。

## 1. 三个标签是什么（不可改写）

| 标签 | 含义 | 不是 |
| --- | --- | --- |
| `supported_in_this_answer` | 本次回答内的证据**已经足够**支持该要点 | 不是"答得完美"，也不是能力认证 |
| `needs_probe` | 还需要就**具体情景**继续追问才能判断 | **不等于**用户没经历、简历有问题、能力不足 |
| `inconclusive` | 本次回答**不足以判断**（没有可用的技术内容） | 不等于否定，也不是"我懒得判" |

## 2. 判定顺序（v2：先判上下文，再判回答）

```
Q0 评测上下文可用吗？（有参考、有前置、问题成立）
   ├─ 否 ─────────────────────────────────────────────→ inconclusive
   └─ 是 → Q2
Q2 这个内容与冻结参考冲突，或引入了参考里没有的关键事实（数字/责任范围/结果）？
   ├─ 是 ─────────────────────────────────────────────→ needs_probe
   └─ 否 → Q3
Q3 回答是否覆盖了该题要点？
   ├─ 覆盖，且没有明显错误 ───────────────────────────→ supported_in_this_answer
   └─ 部分覆盖 / 有错误 / 概念混淆 / 答非所问 ────────→ needs_probe
```

**v1 → v2 的区别**：v1 把"回答里没有可判断内容"也判 `inconclusive`（例如"这块我不清楚"）。
v2 认为那是**上下文可评价、但回答不足**，应判 `needs_probe`（去问，而不是弃权）。
`inconclusive` 只留给 `has_reference=false`、缺前置上下文、问题不成立这三种。

**为什么要改**：v1 让同一个标签承担两种完全不同的意思，gold 就永远摇摆——
F07U 的两处分歧（`obs-05`/`obs-08`）与 v0.2 外审里四处标签争议，根因都是这条边界不清。

**为什么冲突与无来源事实要落在 `needs_probe`**：
它触发的动作是**向用户追问/核实**（谁说的对？这个数字哪来的？），这正是 `needs_probe` 的定义。判成 `inconclusive` 会让系统既不追问也不记录冲突，把最需要用户确认的情况悄悄放走。

## 3. 常见情形对照

| 情形 | 判 | 理由 |
| --- | --- | --- |
| 答对要点、无错误 | `supported_in_this_answer` | Q3 覆盖 |
| 方向对但漏关键前提 | `needs_probe` | Q3 部分覆盖 |
| 明确错误（如"POST 天然幂等"） | `needs_probe` | Q3 有错误 |
| 概念混淆（可见性当原子性） | `needs_probe` | Q3 概念错误，属理解缺口 |
| "这块我不清楚" | `needs_probe`（v2 变更） | 上下文可评价，只是回答不足 |
| 答非所问 | `needs_probe` | 上下文可评价，回答没回答该问题 |
| 上下文缺失（"按刚才那个方案"） | `inconclusive` | 缺前置上下文 |
| 参考是空壳（"见内部文档"） | `inconclusive` | 无可评价依据 |
| 编造来源里没有的数字 | `needs_probe` | Q2 无来源事实 |
| "参与"说成"主导" | `needs_probe` | Q2 责任范围被放大 |
| 回答与材料互相否认 | `needs_probe` | Q2 冲突 → 交用户核实 |
| 题目本身无参考（`has_reference=false`） | `inconclusive`（强制） | 产品规则：无参考不判对错 |

## 4. 与 summary 的分工

标签只回答"下一步该怎么办"；**具体错在哪必须写在 `summary` 里**。一个合格的 observation 应该是：

- 标签决定动作（追问 / 认可 / 弃权）；
- summary 指出具体缺陷（哪一句、缺什么、与什么冲突）；
- `answer_quote` 与 `evidence_id`/`evidence_quote` 可逐字回溯。

因此评分时**标签对但 summary 没说清缺陷**，仍然算不合格（本套件的 `checks` 就是查这个）。

## 5. 边界情形怎么处理（写死在前面，避免事后找补）

1. **同一回答既有错误又有未覆盖要点** → `needs_probe`（动作相同，summary 里都写上）。
2. **回答很长但没有实质内容**（复述题干、泛泛而谈） → `inconclusive`（Q1：没有可判断内容）。
3. **回答与参考表述不同但等价**（措辞差异） → `supported_in_this_answer`；不得因措辞不同判错。
4. **不确定时就低不就高**：宁可 `needs_probe`（会追问），不要 `supported_in_this_answer`（会把未核验的东西当已支持）。但**不要**为了保险一律 `needs_probe` —— 那会让"认可"永远发不出来。
